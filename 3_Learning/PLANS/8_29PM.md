# Paper-Grounded Changes for `3_Learning`

## Summary

Use the two papers to move the project from “DOM GNN predicts axe labels” toward a scalable accessibility audit system:

- From **Towards Scalable Web Accessibility**: add site-level sampling, multimodal page embeddings, auto-check vectors, MLLM-assisted critical element/page discovery, and remediation-ready reports.
- From **Graph4GUI**: change the element graph from only DOM edges into a richer GUI graph with explicit constraint nodes for alignment, same-size, grouping, and multimodal grouping.

## Key Changes

### 1. Add Graph4GUI-Style Constraint Graphs

Create a new graph mode alongside `dom` and future `a11y-tree`:

```text
--graph-source dom
--graph-source dom-constraints
--graph-source a11y-tree
```

Implementation direction:

- Add `GRAPH_SOURCE_DOM_CONSTRAINTS = "dom-constraints"` in `src/graph_sources.py`.
- Add `build_dom_constraint_graph(html_path)` that starts from the current DOM graph, then adds constraint nodes.
- Keep normal element nodes, but add new node types:
  - `element`
  - `alignment_constraint`
  - `same_size_constraint`
  - `grouping_constraint`
  - `multimodal_grouping_constraint`
- Add edges from elements to constraint nodes instead of only element-to-element spatial edges.

Constraint rules to implement first:

- Alignment:
  - left, right, top, bottom, horizontal-midline, vertical-midline alignment.
  - Connect elements whose coordinates are within a small threshold, e.g. `8px`.
- Same size:
  - same width and same height constraints.
  - Connect elements whose width/height differ by less than `8px`.
- Grouping:
  - connect nearby elements with overlapping/close bounding boxes.
  - useful for label/input, card contents, nav items, repeated lists.
- Multimodal grouping:
  - connect text + image/svg/button/icon elements that appear in the same visual group.

Model update:

- Replace or extend `DOMAttentionNet` with a heterogeneous model path, ideally `torch_geometric.nn.HeteroConv`, for `dom-constraints`.
- Keep the current homogeneous model for `dom` so old experiments remain reproducible.

Why:

- Graph4GUI argues that GUI representations should explicitly encode textual content, visual appearance, element type, position, size, and layout constraints.
- This maps directly to web accessibility, where violations often depend on visual/semantic relationships, not isolated DOM tags.

### 2. Add GRASP-Like Page/Site Sampling

Add a new script:

```text
scripts/sample_pages.py
```

Goal:

```bash
python scripts/sample_pages.py \
  --data-dir ../2_Data/browser-use/outputs/axe-core \
  --output ./reports/page_sample.json \
  --sample-size 20
```

Implement a page/site embedding table with:

- Text embedding:
  - reuse sentence-transformer over page text.
- Visual/layout embedding:
  - start simple with layout statistics from bounding boxes.
  - later replace with screenshot ViT embeddings.
- Auto-check vector:
  - vector of axe rule counts per page.
- Linkage vector:
  - initially derive from page URLs and internal links if available.
  - later use a true site hyperlink graph.

Output:

```json
{
  "sampled_pages": [
    {
      "site": "www.example.com",
      "html_path": ".../0.html",
      "cluster": 3,
      "reason": "closest to multimodal cluster centroid"
    }
  ],
  "metrics": {
    "mean_inter_sample_similarity": 0.42,
    "num_clusters": 20
  }
}
```

Why:

- The AAA paper’s GRASP component focuses on representative page sampling using textual, visual, and linkage representativeness.
- This gives your dissertation a scalable audit story beyond single-page node prediction.

### 3. Add Auto-Check Feature Vectors to Training

Currently axe labels are only targets. Add axe summary features as inputs too.

Implementation:

- In `feature_extractor.py`, parse the full axe report into:
  - page-level rule count vector `[NUM_RULES]`
  - node-level impact severity where available
- Store:
  - `data.page_rule_counts`
  - `data.node_impact`
- Use `page_rule_counts` in graph-level prediction or page sampling.

Why:

- AAA’s TPS dataset includes auto-check results as part of the page representation.
- This lets the model learn from deterministic checkers while still adding graph/context reasoning.

### 4. Add “Critical Element” Candidate Extraction

Add a lightweight MaC-inspired pre-audit layer without needing an MLLM yet.

In `predict_site.py`, add `critical_candidates` to the report:

```json
"critical_candidates": [
  {
    "node_id": 123,
    "type": "form",
    "reason": "input form / complete-process candidate"
  }
]
```

Initial rule-based categories:

- `form`
- `search`
- `filter`
- `contact`
- `captcha`
- `login/auth`
- `payment/checkout`
- `navigation`

Later, this can become an MLLM classifier.

Why:

- AAA/MaC emphasizes “pre-audit element localization” so auditors validate candidates instead of manually searching pages.
- This is highly aligned with your proposal’s “targeted remediation” goal.

### 5. Make Reports Remediation-Ready

Extend `reports/prediction.json` entries with:

```json
    "tag": "img",

    "text_preview": ""
  }
}
```

Implementation:

- Add `src/remediation_rules.py`.
- Start with template fixes for the common rules:
  - `image-alt`
  - `button-name`
  - `link-name`
  - `label`
  - `color-contrast`
  - `frame-title`
  - `html-has-lang`
  - `nested-interactive`
- Use predicted rule IDs only if calibrated; otherwise prefer axe rule IDs when `--axe` is supplied.

Why:

- AAA explicitly includes report/remediation as part of scalable auditing.
- This also bridges your proposal toward KG/RAG later.

### 6. Improve Evaluation for the Paper Claims

Add evaluation beyond precision/recall:

For violation detection:

- node precision/recall/F1
- per-rule precision/recall/F1
- threshold sweep
- precision@k
- recall@k
- calibration curve or histogram

For sampling:

- mean inter-sample cosine similarity
- intra-cluster vs inter-sample similarity difference
- cluster coverage
- axe-rule coverage in sampled pages

For reports:

- number of critical candidates found
- overlap with axe violations
- false-positive categories

Why:

- AAA evaluates GRASP using representativeness/diversity metrics, not just classifier F1.
- Your current model has very low precision, so ranking and coverage metrics may be more useful than binary threshold metrics.

## Suggested Implementation Order

1. Add `dom-constraints` graph source using Graph4GUI-style constraint nodes.
2. Add report remediation templates for the top 8 axe rules.
3. Add critical candidate extraction to `predict_site.py`.
4. Add `sample_pages.py` with simple text/layout/axe vectors.
5. Add sampling metrics and threshold-sweep evaluation.
6. Later replace layout stats with screenshot ViT embeddings and add real `a11y-tree`.

## Test Plan

- Unit-test `build_dom_constraint_graph()` on a small synthetic HTML file:
  - aligned buttons create an alignment constraint node.
  - same-width inputs create a same-size constraint node.
  - nearby label/input create a grouping constraint node.
- Smoke-test all graph sources:
  - `--graph-source dom` works.
  - `--graph-source dom-constraints` works.
  - `--graph-source a11y-tree` still raises a clear future-hook error.
- Run prediction on AG Grid and incometax:
  - report still includes existing `predicted_violations`.
  - report now includes `critical_candidates`.
  - report includes remediation suggestions when rules are known.
- Run `sample_pages.py`:
  - produces exactly `sample-size` pages unless fewer pages exist.
  - produces cluster IDs and sampling metrics.
- Confirm old DOM model rejects `dom-constraints` unless trained with that source.

## Assumptions

- Keep the current `dom` pipeline stable for reproducibility.
- Add `dom-constraints` before implementing real `a11y-tree`, because Graph4GUI ideas can be applied now using rendered DOM bounding boxes.
- Start with rule-based MaC-style candidate extraction; use MLLMs later once the pipeline shape is stable.
- Use axe labels as ground truth for now, but present the system as “axe-assisted graph learning,” not as a replacement for human accessibility judgment.
